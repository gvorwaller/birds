# Selective family-description quality review

Task: `td-e78d7b`. The user authorized the production refresh with “Do that now.”

## Purpose

Some published accounts passed factual verification but offered little study value. Pelicans, for example, had a fossil-focused description. This operation reviews the whole published catalog and replaces only accounts for which a materially better, source-supported description can be prepared. It does not regenerate the catalog wholesale.

## Review and publication safeguards

1. Snapshot all 251 current families, their complete published content and sources, taxonomy membership, and publication fingerprints.
2. Review all 250 accounts that were published at the start using Sonnet 5. Assess identification, habitat/range, feeding, voice, and behavior. A concise account can be useful; additional length alone is not an improvement. After editorial inspection, retain 207 accounts and investigate 43.
3. Fetch Animal Diversity Web family accounts where available, otherwise Wikipedia accounts whose scientific name, rank, and avian identity are verified with Wikidata. Preserve complete retrieved prose, revision links, and licensing information.
4. Where family pages are sparse, use explicitly named species/genus examples. For the remaining large source collections, the operator explicitly requests at most six documents. This is a source-example selection, not a reduction of the taxonomy catalog. Preserve the full current membership and list members outside source coverage in the artifact; the summary must identify its examples. For small families whose genus page remains too generic, the editorial operator can prefer individual species accounts. Ordinary background source discovery has no new document limit.
5. Generate a replacement, independently audit every included factual claim against the stored passages, and compare educational usefulness with the existing account. Reject mere rearrangements, name lists, and taxonomic padding. Inspect proposed publications editorially as well. Manual edits receive a fresh source audit and comparison.
6. Dry-run each publication wave. Apply only approved candidates whose original publication fingerprint and current taxonomy hashes still match. Each family update and archive insertion is transactional. Store the predecessor in `family_enrichment_diagnostics` with outcome `quality_refresh_replaced`.
7. Verify preserved publications, refreshed hashes, archives, live source attribution, and the unchanged 180-day refresh interval.

The previously missing Crows and Jays account completed through the normal worker during this review and was inspected separately. It was not part of the 250-account baseline quality review.

## Findings that affected the tooling

- Source support and study usefulness need separate checks. The comparison model sometimes approved superficial changes, so final editorial inspection rejected examples such as a Cisticolas rewrite that mainly added names.
- A source bundle describes available evidence; a short account does not need to enumerate every covered species. The audit prompt now states this explicitly while retaining strict species/genus scope and claim support. A deliberately false Limpkin control was rejected after this clarification.
- Exact taxon discovery through Wikidata's Action API avoids the expensive SPARQL ancestry scans that encountered rate limits during the initial review. Search finds candidates; P225 scientific name, P105 rank, and P171 ancestry are checked separately. Search pagination is followed, entity requests are batched, and rate limits are honored. See the [official entity API](https://www.wikidata.org/w/api.php?action=help&modules=wbgetentities).
- Provider JSON-schema constraints do not replace local content validation. Unsupported length constraints were removed from the recovery request schema; local paragraph, heading, evidence, and length validation remains in force. See [Anthropic's structured-output limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

## Reproducible operator tools

- `scripts/review-family-quality.mjs`: resumable catalog review.
- `scripts/improve-family-quality.mjs`: source collection, generation, independent audit, comparison, and checkpointing.
- `scripts/repair-family-quality.mjs`: explicit selected-family recovery from already collected sources.
- `scripts/family-quality-control.mjs`: honors the production family pause, main worker pause, and provider cooldown between requests. AI calls run against the isolated test database's existing metered Sonnet integration; production publication is a separate guarded operation.
- `scripts/build-family-quality-operator.mjs`: builds the publication entry point.
- `scripts/apply-family-quality.ts`: dry-run by default; requires `--apply` for publication.
- `src/lib/server/family-quality-refresh.ts`: compare-and-set publication and archival logic.

Private snapshots, full source texts, paid drafts, audits, editorial decisions, wave manifests, and verification results are retained under `.local/family-quality-*`. Do not commit these source bundles or credentials. On production, the one-time publication bundle and manifests live under `/opt/birds/.local/`; they update data without replacing application code or restarting services.

Help was reviewed: it already explains source-grounded summaries, scoped species/genus accounts, linked attribution, and six-month refresh. This is a one-time content operation with no new user workflow, so Help and Version History do not require a release entry. The local tooling and prompt changes have not been committed or deployed as application code.
