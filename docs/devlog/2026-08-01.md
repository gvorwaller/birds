## The load-bearing decision: `?loc=` must not re-run the loader

Focusing a place changes the URL. The obvious implementations both fail:

1. **Hash + native `history.replaceState`** — `replaceState` creates no history entry, so Back can
   never clear focus, and SvelteKit 2.65 monkey-patches both native history methods to warn
   against them (`client.js:110-121`).
2. **Shallow routing via `pushState` from `$app/navigation`** — genuinely never runs `load`, but it
   **does not assign `page.url`**. It stores `[PAGE_URL_KEY]` = the URL of the last _real_
   navigation (`client.js:2472-2477`) and restores `page.url` from that on a shallow pop
   (`:2828-2851`). So `page.url` and the address bar diverge, and a design that reads focus from
   `page.url` cannot observe a client-selected `loc` at all.

What actually works is a **plain `goto('?loc=…')`**, enabled by deleting one line. SvelteKit tracks
load dependencies per URL access: `searchParams.get/has/getAll` records a single key, while any read
of `search`/`href`/`pathname`/`toString`/`toJSON` marks the **whole URL** (`make_trackable`,
`src/utils/url.js`). The root loader already read `place`/`back`/`dist` per-key — and then read
`url.search` to mint `returnTo`, which is what made _every_ param change re-run `geoTargets()` and
its per-species fan-out.

Moving `returnTo` into `+page.svelte` (from `$app/state`'s `page.url`, which is populated under SSR
too) leaves only per-key tracking. `loc` is then untracked, so a focus change is a client-side
navigation that reuses server data — with real history entries, working Back/Forward, and
`afterNavigate` firing. The fix and the enabler are the same edit.

**Measured, not assumed:** CODEX drove the browser and confirmed the dev-server loader counter did
not advance across focus, focus-change, Back, Back-again, and Forward.

### The invariant is now a test, not a comment

`src/routes/home-loader-url-tracking.test.ts` fails if the loader reads a whole-URL property or
registers `loc` as a tracked key. This is not theoretical: temporary gate instrumentation logged
`url.pathname + url.search` and **created the exact dependency it was measuring**, producing a false
gate failure. The guard was mutation-tested (reintroduce `url.search` → test fails with an
actionable message) before being trusted.

## Review rounds

Three review passes, each finding things the previous could not.

**CODEX3, plan review (×2).** Caught the `page.url` problem above before implementation, plus the
`ObsMap` bounds bug: it counts _entries_, not unique coordinates (`ObsMap.svelte:124-126`), so
"focused center + one marker at those coordinates" totals 2 and runs `fitBounds` on a zero-area box.
Focus mode passes `center = null` instead, taking the single-point `setCenter`/`setZoom(11)` path.

**CODEX, browser round 1.** Three P1/P2 defects: focused cards showed whole-area aggregates
(`65 locations · 110 birds` on a card displaying one place); 20 place matches pushed the focused
birds 3,219px down a 390px screen, defeating the action the user had just taken; and a stale `loc`
survived forever in `view === null` states because self-heal was guarded on a non-empty index.

**CODEX3, code review of the full diff.** Nine defects a green browser pass could not reach. The two
that mattered:

- **Identity was implemented twice and the copies disagreed.** `reconcile()` _chose_ which host
  absorbs a coordinate-only record (first match wins) while `placeRecordBelongsTo()` independently
  re-derived membership by epsilon — so with two hosts in range a species could attach to a place
  whose own counts never included it, and the owner flipped with iteration order. `PlaceMatch` now
  carries `memberKeys` (the exact folded raw keys) and membership is a set lookup. Ambiguous folds
  are refused outright rather than resolved arbitrarily.
- **A focused card could open the wrong place in Google Maps.** `SpeciesActivity.googlePlaceId`
  follows the whole-area latest observation, and narrowing didn't recompute it — while
  `mapsPlaceUrl` prefers `query_place_id` over coordinates (`geo.ts:118-124`). `speciesAtPlace` now
  collapses to one canonical record taking every identity field from the match.

Also: the token matcher used greedy first-fit, which fails when an earlier query token consumes the
only candidate a later one needs (`park parkside` vs `Parkside Park`) — replaced with
augmenting-path bipartite matching.

**CODEX, browser round 2 — APPROVED.** All fixes verified. Two cases I had written off as
unconstructable turned out to be reachable, and one proved the bug had been real and user-visible:
`bar harbor` previously rendered a **duplicate pair** for Three Pines Bird Sanctuary and now renders
one canonical row. `bar bar harbor` against `Bar Harbor--Bar Island Bar` exercised the matcher fix.

## Withdrawn claim

The plan said the escape hatch "works without JS". **False, and withdrawn rather than left as an
aspiration.** The anchor renders only when a typed query yields zero place hits, but the filter is
client state — SSR always renders it empty and nothing without hydration can change it, so the link
is statically unreachable with JS off. Place search is JS-required by construction; the top "Place"
GET form remains the no-JS path to the same geocoder.

## Deliberately preserved quirk

`normalizePlaceName` strips the stopword `us` _before_ the `xx-xx` state-code rule can match
`us-fl`, leaving a stray `fl` token; the state-code rule only ever fires for county codes like
`fl-du`. Left as-is — it feeds `placeNameScore`, which decides real Google Places matches — and
pinned by golden cases. It does not hurt search: the noise sits on the eBird-name side, where only
_query_ tokens must be satisfied.
