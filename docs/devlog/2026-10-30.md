# 2026-10-30 Devlog

## td-6093ae: Admin → Taxonomy refresh (in progress)
The owner asked whether the eBird 2026 taxonomy update (from Oct 27) had reached the app.

**It had not.** `sync_taxonomy` was a manual button in Settings, pressed once on 2026-09-11. Prod is still on the 2025 taxonomy: 17,891 taxa, 11,167 of them species.

eBird has switched: a read-only GET of `/ref/taxonomy/versions` returned `[{"authorityVer":2026.0,"latest":true},{"authorityVer":2025.0,"latest":false},…]`.

**Prod, measured read-only:**
- 14,157 stored frequency locations: 6,717 regions and 7,440 hotspots.
- Willet is held by 3,692 of them and Marsh Wren by 4,333.
- 884 locations were loaded since the last sync. The newest load was 2026-10-18, before eBird switched.
- No frequency job ran after Oct 27.
- 5,266 locations have a truncated unmatched-name sample (only 20 names are stored).

**The owner wants a permanent admin feature, not a workaround.** Decisions:
- The sync moves out of Settings to admin only.
- One button runs back up → sync → compare.
- It gets a new Taxonomy tab.

Plan: `docs/2026-10-30-taxonomy-refresh-plan-CC.md`, revision 2. CODEX1's hostile plan review gave 2 P1, 8 P2 and 2 P3; all were incorporated, as listed in its "Review changes" section.

**Built so far:**
- **Migration 0099:** `taxonomy_runs`, `taxonomy_backups` and `taxonomy_backup_rows` (every `taxonomy_cache` business column), `taxonomy_changes`, `taxonomy_refresh_batches`, `taxonomy_refresh_locations`.
  - A unique partial index allows one open run at a time, failed or not. A failed run is resumed, never replaced.
  - `requested_by` is `ON DELETE SET NULL`. Nothing cascades from users or jobs.
- **`src/lib/server/taxonomy-refresh.ts`:**
  - **Pure parts:** `classifyChanges` covers every field, null-safe, with banding treated as a set and taxon order as a number. Kinds: removed, added, category, scientific, common, report_as, other. The affecting set takes old species that were removed, demoted or renamed (a common-name-only change counts), plus both reporting parents of a report_as change. There is an order-independent `taxonomyHash`.
  - **Run state machine:** started → backed_up → applied → after_backed_up → compared → done. Each stage is claim-fenced and committed on its own. "Applied" is written inside the replacement transaction with the target hash. The after-backup is checked against that hash. A retry never refetches once the run is applied.
  - **Workset:**
    - changed_species, from `species_frequency` by code;
    - now_matches, from the stored unmatched sample checked with the real `buildMatcher` (positive evidence only);
    - loaded_since_sync, a disclosed superset;
    - carried_over, from earlier unfinished runs, which are then superseded.
  - **Dispatch:** fixed batches of 200 `refresh_loc` jobs (force), each with its batch row and location dispatch, all in one transaction holding the run row. The clicking admin's eBird login is the prerequisite.
  - **Progress:** reloaded, queued, failed, unfinished, not queued or removed, derived without extra writes. Retry unfinished re-queues failed and unfinished locations.
- **Other code:**
  - `replaceTaxonomy` gains `onApplied`.
  - `ebird.ts` gains `fetchTaxonomyPayload` and `latestTaxonomyVersion`, the latter cached a day; anything but exactly one `latest:true` entry gives null.
  - New traffic class "Taxonomy versions".
  - New dedup key `taxonomy_refresh:<run>:<batch>`.
- **UI:**
  - `TaxonomyPanel.svelte` on a new Admin → Taxonomy tab: instructions, status (ours and eBird's latest, with Update available), the run's steps with **Try again**, changes, locations to reload with **Refresh affected locations** and **Retry unfinished**, life-list orphans, and history with backups.
  - The panel polls `GET /api/admin/taxonomy?run=` while work is under way, then reloads its data.
- **Settings:** ⟳ Sync is removed. The row points admins to Admin → Taxonomy.
- **Wording:** help gains an "Admin: Taxonomy refresh" section, and its life-list paragraph is updated. The two life-list messages in `ebird-account.ts` and the About history are updated.

**CODEX1 code review (2026-10-31 UTC): not clean, 8 P2 and 1 P3. All fixed:**
1. **DB tests could supersede history they don't own.** `compareRun` takes the earlier runs it may carry over and supersede; the default is all, and tests pass their own. A regression test shows an out-of-scope run untouched.
2. **A finishing failure couldn't be resumed from the card.** A compared but unfinished run is now "open": **Try again** resumes it through `startOrResumeRun`, tested through that action path.
3. **Polling stopped while finishing.** The card now polls while the run's job is active, whatever the stage. A browser regression covers finishing → done.
4. **No-JS posts dropped the tab and the message.** Form actions carry `&tab=taxonomy` (and `&run=` when one is selected). Action results carry their `section`.
5. **Starting a run from an older run's view.** The action returns `runId`, and the card goes to that run, keeping the message.
6. **The recorded version could come from a day-old cache.** The run now asks eBird's versions endpoint fresh (`fetchLatestTaxonomyVersion`) and fetches the taxonomy pinned to that version; the cached one only feeds the status line.
7. **The batch error outlived its fix.** It is now shown only while that batch still holds failed or unfinished locations.
8. **A failed life-list orphan count showed as zero.** It is now `null`, shown as "unavailable".
9. **Per-taxon stored-location counts were missing for detail-only changes.** They are now counted for every changed code.

Also added: tests for pruned and cancelled batch jobs, a stale claim during comparison, the app role's grants, and the version pin. Phase 0 EXPLAIN and band-rollup timings are recorded in the plan.

**CODEX1 round 2:** the 9 fixes were confirmed. One new P1 in the tests: start/resume could adopt a pre-existing compared run, and cleanup would then delete it. Fixed:
- `beforeAll` refuses any unfinished run, compared included.
- Every start/resume goes through `startOwned`, which refuses before calling `startOrResumeRun` if any unfinished run is not this file's, and checks the run it returns before cleanup may touch it.
- A regression shows a foreign compared run is left untouched.

Also added explicit resume tests after "applied" and after "after_backed_up".
