## Stuck pages (td-1cb094): the browser reports its own navigations
The owner's go was "build 1". The server can't see a phone that hangs after it has answered, so the browser now reports on itself.
- **What is timed:** each navigation, by SvelteKit's milestones.
  - **Start:** the `navigating` store, not `beforeNavigate`, which SvelteKit skips while another navigation is loading (CODEX1 P1).
  - **Ready to draw:** `onNavigate`.
  - **Finished:** `afterNavigate`.
  - Each milestone is matched to its navigation object.
- **Heartbeat:**
  - It beats every 500 ms; a gap of 2 s or more while visible is a freeze.
  - Tab state is saved to localStorage every 2 s and at each milestone.
- **Recovering a killed page:**
  - The next page of the app reports it.
  - In the installed app, which runs one page at a time, that happens at once.
  - A browser tab must be visible and miss two BroadcastChannel roll calls 10 s apart.
  - A hidden tab is never reported, because it may only be suspended.
  - A reload mid-navigation is reported as `reloaded`, unless it was SvelteKit's full-page fallback landing on its destination.
- **Report kinds:** slow, superseded (a second tap), unfinished, reloaded, lost (stopped on screen with nothing loading), freeze.
- **Ownership and privacy:**
  - Each report keeps its own build and account; only that account sends it.
  - Error text has addresses cut to their path, and query strings and credential-like values blanked.
- **Server:**
  - `POST /api/client-stalls` accepts any signed-in account, viewers too.
  - The `client_stalls` table comes from migration 0093.
  - Each account is capped at 300 reports a day, under a per-account advisory lock.
  - Reports are pruned after 30 days.
- **Admin:** Admin → Metrics → **Stuck pages**, above Slow pages:
  - a count per page over 7 days;
  - the latest reports, with who, the device ("iPhone · Safari 27.0.1 · installed app"), the deploy, and one plain sentence of what was measured (no guessed causes).
- **Review:** CODEX1 (high).
  - **Round 1:** 10 problems, all fixed.
  - **Round 2:** 4 more, all fixed:
    - redaction missed JSON and `api_key`-style fields;
    - a tab left open across an account switch could post under the new session; the server now refuses a mismatched `accountId` with 409;
    - another open tab could mislabel SvelteKit's successful fallback as reloaded;
    - on-screen waiting after a return from the background was not counted.
  - **Round 3:** 3 more, all fixed:
    - an escaped or unterminated quote still leaked part of a password;
    - the redaction pattern could freeze on long text; raw text is now cut to 1,000 characters first, the label scan is anchored at word starts, and the endpoint refuses error text over 200 characters;
    - the panel subtracted a wall-clock time from an on-screen time; "ready to draw" is now on-screen time too, and the sentences live in `describeStall()` with tests.
  - **Round 4:** 1 more, fixed: a backslash left dangling by the 1,000-character cut inside a quoted value let the rest of the credential through. A trailing backslash now belongs to the cut-off quoted value; there are tests for both quote styles, and they fail without the fix.

## Server freezes (td-b07462): the web process reports when it stops responding
The owner's go: "much less likely than phone issues, but it's worth filling in the numbers with that metric."
- **Detection:**
  - A 100 ms timer measures, on the monotonic clock, how late it fires.
  - A freeze is a lateness of 1 s or more.
  - It is written one tick after it is noticed, so GC timings that arrive late still count.
- **What each freeze records:**
  - **Requests already running when it began.** They are counted in full, and the oldest 10 are listed with how long each had run. Requests and named operations are kept as start/end spans for 2 minutes after they end, so work that finished the moment the freeze ended still counts.
  - **Requests that started while it lasted.**
  - **Named operations** (`trackBusy`): the hotspot search index rebuild and the verified hotspot list rebuild.
  - **GC pause time inside it**, summed from 10 ms slots on the monotonic clock.
  - **Memory and the deploy.**
- **Storage:**
  - `server_freezes` comes from migration 0094.
  - The table is pruned after 30 days, and writes are capped at 60 an hour.
  - Abandoned requests are swept every minute: a body SvelteKit replaced with a 304 is never read.
- **Slow pages:**
  - A row that overlapped a freeze says so ("its time includes it, whether it caused it or waited on it"), and the by-page summary counts them.
  - Rows now store their real finish time (`finishedAt`), not the time the database write happened.
- **Admin:** Admin → Metrics gets a **Server freezes** card, with a 7-day count, total frozen time, the longest, and the latest freezes described in one sentence each (`describeFreeze`).
- **Limit, stated in the panel:** a request that arrives during a freeze waits in the operating system's queue before Node accepts it. It is not listed, and its wait is not in Slow pages; only the freeze record shows that time.
- **Verification:**
  - A production build on birds_test, paused with SIGSTOP for 3 s with two requests inside, recorded a freeze of about 2.9–3.0 s with both requests listed and both Slow pages rows marked.
  - Pausing it with requests arriving during the stop recorded the freeze with none listed.
- **Review:** CODEX1 (high), 2 rounds.
  - **Round 1:** 5 problems, all fixed:
    - work ending at the freeze's end vanished before the timer ran;
    - abandoned requests leaked;
    - more than 10 running requests were miscounted as arrivals;
    - the overlap used the database-insert time;
    - a 200-entry GC buffer lost pauses.
  - **Round 2:** PASS.
  - I also made one fix of my own: lateness is measured on the monotonic clock, so a wall-clock correction is not a freeze.

## Hotspot search index: rebuild only on real changes, never freeze (td-877997)
The owner's question: "there should be absolutely zero reason for it to ever get rebuilt until the underlying data changes, right?" Right in principle, but it rebuilt for two wrong reasons.

**What the index is.** Hotspots & data search reads an in-memory index of every country, region and county, every loaded row, and every hotspot in the cached official lists. On prod that is 19 region lists with 268,082 entries, about 186k hotspots and ~64 MB. The trip export and the species query engine use the same lists (a second, separate build) to tell official hotspots apart.

**Why it rebuilt:**
1. **Refetches counted as changes.** The revision used each cached list's `fetched_at`. Lists expire after 24 h, so whichever page next needed one refetched it, and eBird's identical hotspots still changed the revision. Prod, 10-25: 20 of the 24 lists were refetched at 02:00 UTC during the owner's Hotspots & data session, and the 02:31 search rebuilt.
2. **Restarts dropped it.** The index lived only in memory, so every deploy or restart threw it away.

Genuine changes (loads) are rare: none in the last 7 days.

**Why a rebuild froze the server.** It is one long stretch of JavaScript on Node's single thread, about 7 s on the droplet. Every search also scanned and re-normalized all 186k names, about 1 s per keystroke search on prod, which also held the server.

**Fixes (owner's go, 1–4):**
1. **Content-only revision (migration 0095).**
   - A trigger fingerprints only the fields the index reads.
   - Whole-payload comparison is no use, because each entry's `latestObsDt`, `numSpeciesAllTime` and `numChecklistsAllTime` change daily.
   - The trigger moves `content_changed_at` only when the fingerprint changes; the revision uses that.
   - The loaded half of the revision dropped `fetched_at` and `updated_at` too.
2. **The build no longer blocks.**
   - The list query is read through a cursor, 2,000 hotspots per round trip. node-pg parses every row in one socket read at once: 545 ms locally for the whole list.
   - Build loops and the search scans pause every 2,048 items.
   - Names are normalized once, at build time.
   - The official-hotspot ID set now comes from the index instead of a second build.
3. **Keep the current index while a new one builds** when only the hotspot lists changed. A change to loaded data (the owner's own load) waits, so the search shows it.
4. **Built at startup and checked every minute.** `/api/health` reports `hub_index`, and the deploy waits for `ready` (warns after 180 s, never fails).

**Measured** with prod's 19 lists copied into birds_test (read-only from prod, deleted afterwards):

| | Before | After |
|---|---|---|
| Cold search | 2,086 ms | 146 ms (index built at startup in ~2.4 s) |
| Worst server answer during the build | 732 ms | 22 ms |
| Worst server answer during searches | | ≤4 ms |

- A same-content refetch did not rebuild.
- After a hotspot rename, the search answered at once from the current index; the background rebuild took 2.4 s, and then the new name was found.
- Local times are roughly 10× faster than the droplet.

**Review:** CODEX1 (high), round 1: 2 problems, both fixed, each with a mocked-database regression test that fails without the fix.
- A search waiting for the owner's load could receive a rebuild that was already running and had read the data before the load. Callers that need a revision now wait for any running build, check again, and rebuild until it fits (at most 3 rounds).
- A failed sibling read could leave the list cursor running beside the next build. The cursor now stops, and the build fails only after the cursor has closed.

**Memory**, with prod-sized lists under prod's `--max-old-space-size=384`: a rebuild beside the live index peaked at 209 MB of heap and 438 MB RSS. Prod's old rebuilds logged 401–421 MB RSS; PM2 restarts at 1 GB.

**Deploy note:** migration 0095 fingerprints the US list (158k entries) inside the migration transaction, so expect a few seconds of lock on `ebird_cache` during the migrate step.

**Deployed** bab8ce9. On prod the startup build took 9.3 s for 242,750 hotspots, and the deploy saw the index ready about 10 s after health OK. All 24 hotspot cache rows were fingerprinted. No server freezes were recorded during the build.
