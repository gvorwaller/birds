**Query speed:**
- The planner's first choice walked every taxon's records, taking 500 ms on prod. Filtering a coordinate box first (a materialized CTE) took 68 ms.
- Migration 0098 swaps the (lat, lon) btree for a GiST index on `point(lon, lat)`. It was measured on birds_test with real Nordland plus 2M synthetic points spread over Norway: 14 ms against 17 ms for a 50 km box (index scan 1.6 ms against 4.5 ms). The gain is small, but it suits a 2-D search.

**Built:**

- **Card:** `ExternalNearCard.svelte`. Needs first; per species its places with distance and "in N of M Octobers". The rest of the needs and the seen species sit in `<details>` folds. It also shows the busiest 5 places (Map, plus Add to trip when the place's best report is placed within 1 km) and the municipalities, each linking to "Where and when to look".
- **Forecast loader:** awaits the card with the shell, so it renders without JavaScript; a failure is logged and the card left out. The eBird analysis stream adds the sources that cover eBird's region but have nothing loaded, for a Load button (not for viewers). The page gets the shared `queueExternalLoad` action.
- **Pointer line:** a line in the eBird card links to the card and is never added into the eBird numbers.
- **Help:** one bullet in "Reports from other sources".

**Checks:**

## td-a6f8a1: Hotspots & data — Location fields narrow the search
**Owner report:** the slow list showed a search for "Florida". The owner wanted just the state of Florida and its species count; the typed search returned every place and hotspot with "Florida" in its name or context. **Owner decision:** keep the typed search as it is; add the Field Guide's location fields; a location limits results to places inside it, down to hotspot level.

**Measured on prod (read-only):** US-FL is loaded as a whole (632 species, 2016–2025), with 68 county rows and 3,979 hotspot rows under it. Opening Florida in the inventory downloads 809 KB (`/api/region-detail?region=US-FL`).

**Built:**
- **Fields:** under the search box: Country, State / region, County / equivalent and Verified hotspot. These are the Field Guide's SearchableSelect fields, list controller and `/api/guide-locations`, so both pages offer the same places. They need JavaScript; without it a note says so, and a shared link with a location still renders on the server.
- **Results:**
  - **A location alone** shows that one place, e.g. "Showing Florida" with "loaded, current · 2016–2025 · 632 species".
  - **Text and a location** show only matches inside it ("… for “park” in Florida").
  - **No location** leaves the search as before.
- **URL:** `inCountry`/`inRegion`/`inCounty`/`inHotspot`, parsed with the Field Guide's rules. `country` and `region` already preselect the Load form on this page, so the names differ. Typing keeps the location; a map point and Clear search remove it.
- **Server** (`hub-discovery.ts`):
  - `resolveWithin` gives the location's name, its context and whether it is known.
  - A place is inside the location when the location is its own code or one it is recorded under.
  - A hotspot is inside a place when its official record or its loaded row puts it there.
  - A location that is not known says so instead of showing an empty list.

**CODEX1 (high), round 1: three P2s, all fixed:**
1. **SvelteKit's `replaceState` changes the address bar, not `page.url`, and Back reloads the old `page.url`.**
   - **Effect:** links, paging and Back after a live search used the old address. This also affected the existing typed search: "Next →" after live typing had no `find`.
   - **Fix:** the page keeps the address on screen (`liveHref`) and builds every link and the next search from it. It saves that address in the history entry's state, and Back re-runs the search from it.
   - **Do not change:** PathNavigation keeps the `page.url` address. Navigation-context rewrites the address bar from `page.url` whenever that prop changes, which undid every live address (found in a browser trace).
2. **An offered hotspot could be "not known".** The dropdown lists from the loaded row's region, while the search preferred the official list. The fix is the either-source rule above, with a new conflicting-ancestry fixture.
3. **A search still running could repaint or rewrite the address after leaving the view.** The fix: `beforeNavigate` and the navigation effect cancel it, and the sequence is checked again after the response is read.

**CODEX1 (high), round 2:** findings 2 and 3 closed; two new P2s, both fixed:
1. **A fresh navigation inherited the saved live address.** Navigation-context merges page state into `goto`, so the next page looked like a Back restore and went back to the old search.
   - **Fix:** a restore runs in `afterNavigate`, only for a Back/Forward move (`popstate`). It runs only into the entry that saved the state: `hubBase` (that entry's `page.url`) must match.
2. **The trail ("Your path") still saved the address from before the live search.**
   - **Fix:** `currentHref()` in `navigation-context.svelte.ts` now writes back the address the browser shows, not `page.url`. The two differ only after shallow routing, because SvelteKit writes history before it renders a navigation.
   - **Effect:** PathNavigation follows the live address. "Your path" returns to the live view even after the next page reloads.
   - **Test:** a new adapter test fails when the change is reverted.

**CODEX1 round 3:** both round-2 fixes confirmed, and no problem found in the `currentHref()` change after tracing redirects, hash links, preloads, the reload bridge and other shallow routing. One P2, fixed: Back after a live **clear** (empty box) brought the old typed results back. The restore now also restores a cleared search; the browser check fails when that line is reverted.

**CODEX1 round 4:** confirmed clean, with no new finding. Its note: the second Forward/Back check does not re-read the search box (the first one does).
